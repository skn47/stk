# 11: `stk config` — show/create + precedence chain

**What to build:** `stk config` / `stk config --create` shows or creates the STK config file. Configuration precedence is `CLI flags > environment variables > repository/project config file > global config file`, with no separate runtime "Codex-detection" layer — `stk init --codex` (ticket 12) simply writes to the same project config this ticket reads.

**Blocked by:** 01

**Status:** done

- [x] `stk config` prints the effective, resolved configuration (after precedence is applied).
- [x] `stk config --create` writes a config file with sensible defaults if none exists, and does not clobber an existing one.
- [x] Precedence is enforced in the documented order: CLI flags win over env vars, which win over repository/project config, which wins over global config.
- [x] The `intent`, `session_memory`, and `session_ttl_minutes` config keys are accepted and parsed (schema forward-compatibility) but have no behavioral effect this release.
- [x] Tests cover at least one case per precedence level overriding the one below it.

**Implementation notes:**
- New `config::settings` module holds the pure precedence-merge logic (`Settings`/`PartialSettings`/`resolve`), fully unit-tested with literal TOML strings and hand-built env structs -- no real filesystem or env vars touched. `verbs::config` is the thin production shim: reads `.stk/config.toml` (project) and `$HOME/.config/stk/config.toml` (global, `$XDG_CONFIG_HOME` respected), builds the env layer from real `STK_BUDGET`/`STK_INTENT`/`STK_SESSION_MEMORY`/`STK_SESSION_TTL_MINUTES`, and calls `resolve`. `--create` only ever writes the global file (matching the real `rtk config --create`'s single-location behavior, confirmed against the installed binary) -- ticket 12's `stk init`/`stk init --codex` own writing project config.
- Since env-var/`$HOME`/cwd resolution is genuine OS-level global state, its integration tests (`tests/config_verb.rs`) spawn the real compiled binary with an isolated `HOME`/cwd per case, matching this repo's established convention for OS-level behavior rather than racing other tests' env vars in-process.
- Code review caught and fixed 8 issues: an out-of-range (negative, or too-large) integer config value silently wrapped via an unchecked `as` cast instead of erroring; a malformed env var value (`STK_BUDGET=5ooo`) was silently discarded via `.ok()` instead of erroring like the equivalent malformed-file case; `global_config_path()`'s `HOME`-unset fallback produced a cwd-relative path -- the exact bug `src/history.rs`'s `cache_dir()` already fixed once, now given the same absolute-path fallback; `render()` hand-formatted TOML strings with no escaping, corrupting output for an `intent` value containing a quote or backslash -- replaced with the `toml` crate's own serializer; config file reads collapsed every I/O error (permission denied, etc.) into "file doesn't exist" via `.ok()` -- now only `NotFound` is treated that way; the "(default config...)" note was gated only on the global file's existence and could sit directly above a project-config-driven value, falsely implying it was a default -- reworded to make no claim about *why* a value is what it is; `create_config`'s `exists()`-then-write was a TOCTOU race between two concurrent `--create` runs -- replaced with atomic `create_new`; and `stk config`'s arg parsing silently ignored any unrecognized/misspelled flag -- now errors, matching the global option parser's strictness.
- Deliberately not wired into this ticket: no other verb (`compile`, `read`, `grep`, ...) consults `config::settings::resolve` for its budget default -- each still gets its budget solely from the `--budget` CLI flag. The ticket's acceptance criteria scope this ticket to `stk config` itself; wiring resolved config into every other verb's defaults is a separate, much wider change not requested here.
